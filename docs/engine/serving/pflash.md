# Prefill compression: quality and TTFT harness

Prefill compression shortens a long prompt before the target model prefills it: a small scorer reads the whole
prompt, the parts that matter for the request are kept in their original order, and each gap is replaced by a
one-line marker. The target then prefills a fraction of the prompt, so the time to first token drops.

It changes what the model reads, so it can change the answer. It is neither bitwise nor a numeric approximation; it
has its own exactness class, **LOSSY**:

- it runs only when the server was started with `--prefill-compression auto` **and** the request carries
  `"prefill_compression": "auto"`; a request without the field takes today's path unchanged;
- every fallback (prompt below the threshold, flat scores, scorer failure, no time saved, tools present) prefills
  the full prompt and must answer exactly like a request without the field;
- every reply to an opted-in request carries a receipt: `usage.timings.pflash` =
  `{"raw": N, "kept": M, "reason": "compressed" | "below_threshold" | "flat_scores" | "scorer_failed" | "breakeven" | "tools" | "off", "ms": T}`.

`tools/pflash_bench.py` is the harness that decides, per engine, whether the feature may be offered. It measures both
arms on the same questions against a running server. The server side of the request field is a separate change;
against a server without it the harness reports `NOT_APPLIED` and never a comparison.

## What it runs

Every question is sent twice with greedy decoding: arm `full` (the plain request) and arm `pflash` (the same request
plus the field). The arm that goes first alternates per question. A short tag in the system message differs per arm
so that the second request cannot reuse the cached prefix of the first (`--cache-bust arm`, the default; `item` and
`off` exist for prefix-cache studies). A pair in which either reply still reports more than `--cache-tolerance`
cached tokens is dropped from the TTFT columns and counted.

| set | source | metric |
|---|---|---|
| `niah` | generated by the tool (seeded filler, one needle per prompt at depths 0-100 %); `--niah-haystack FILE` uses real text as filler | the number appears in the reply |
| `ruler` | built from a SQuAD-format or HotpotQA-format file (`--ruler-file`): gold document(s) plus shuffled distractor documents up to the context size | any reference answer appears in the reply (case-insensitive) |
| `longbench2` | LongBench v2 `data.json` (`--longbench2-file`), four choices | the letter in `The correct answer is (X)` |
| `longcodeqa` | LongCodeQA records with `prompt` and `correct_letter` (`--longcodeqa-file`) | `Final Answer: X`, else a trailing letter |

The tool downloads nothing; the dataset files are passed by path. `--ctx 16k,32k,64k,128k` sets the context
buckets (`k` = 1,024 tokens). Generated prompts (`niah`, `ruler`) aim at `ctx x --fill` estimated tokens (default
1.1, so a prompt of the 16k bucket sits above a 16,384-token threshold); file-based questions land in the smallest
bucket that holds them and the rest are counted as skipped. Sizes are estimated with `--chars-per-token` (default
4); the report shows the real `prompt_tokens` of the full arm.

```bash
# both arms, four context sizes, generated set only
tools/pflash_bench.py --base-url http://127.0.0.1:8080 --engine glm --sets niah --ctx 16k,32k,64k,128k \
    --arms full,pflash --rows rows.jsonl --receipt receipt.json --gate

# all sets
tools/pflash_bench.py --base-url http://127.0.0.1:8080 --engine glm --sets niah,ruler,longbench2,longcodeqa \
    --ctx 16k,32k,64k,128k --ruler-file squad.json --longbench2-file data.json \
    --longcodeqa-file final_dataset.json --rows rows.jsonl --receipt receipt.json --gate

tools/pflash_bench.py --from-rows rows.jsonl --gate         # report again, call nothing
tools/pflash_bench.py --sets niah --ctx 16k,32k --dry-run   # build the prompts, print their sizes
```

`--rows` appends one JSON line per request and an existing file is resumed (failed requests are retried).
`--extra-json` merges fields into every request of both arms, for example a switch that turns thinking off.
`--no-stream` asks for one JSON reply; TTFT then comes from the server's `timings.ttft_ms`.

## What it reports

One row per set and context bucket, one per set, and one for everything:

- **full / compressed**: correct answers of each arm over the same questions; **change** is their difference;
- **95 % interval**: seeded paired bootstrap of that difference, in answers; **lost / gained**: answers that flipped;
  **p**: exact two-sided test on the flipped answers;
- **TTFT** medians of both arms on the client clock and **speed-up**, the median of the per-question ratios;
- **kept**: median `kept / raw` of the receipts; **scorer ms**: median `ms` of the receipts;
- **applied / fallback / none**: replies with `reason=compressed`, with another reason, and without a receipt.

A fallback reply whose text differs from the full arm is reported as a fallback mismatch: that is a server defect,
not a quality result.

`--gate` turns the last row into a verdict and an exit code:

| verdict | exit | meaning |
|---|---|---|
| `PASS` | 0 | compression was applied, no fallback mismatch, the accuracy change is not below `-gate-max-mean-loss` (default 0.02) and the low end of the interval is not below `-gate-max-low-loss` (default 0.06), both as fractions of the paired answers |
| `FAIL` | 3 | one of those conditions does not hold; the report lists which |
| `NOT_APPLIED` | 4 | no reply carried `reason=compressed` |
| - | 2 | bad arguments, or requests failed (their pairs are excluded and counted) |

An engine offers the request field only after a `PASS` on these sets; the receipt (`--receipt`) records the
configuration, every cell of the table and every request without its text.

## Tests

`python tests/pflash_bench_tests.py` runs on the CPU with synthetic fixtures and a local stub server: set builders,
scoring rules, receipt parsing, the interval and the exact test, the gate verdicts, resume, and the end-to-end path
in streaming and non-streaming mode.
